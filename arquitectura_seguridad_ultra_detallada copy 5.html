Definición técnica de puntos clave (para el cliente)
1. ¿Cuándo aplicar Always Encrypted (cifrado de columna donde el motor no ve texto claro) frente a TDE (Transparent Data Encryption, cifrado transparente de datos)?

TDE (Transparent Data Encryption, cifrado transparente de datos) se aplica a toda la base: es el «seguro» de los ficheros físicos del motor y de las copias estándar; transparente para la mayoría de consultas. Always Encrypted (cifrado de columna donde el motor no ve texto claro) es columna a columna para datos concretos (identificadores personales muy sensibles, secretos de negocio, etc.): permite argumentar ante auditoría que ni administradores de plataforma con privilegios habituales acceden al valor en claro sin canal autorizado (según modo y roles).

2. Flujo del DDM (Dynamic Data Masking (enmascaramiento dinámico de datos)) en cadena

El dato reposa cifrado a nivel volumen gracias a TDE (Transparent Data Encryption, cifrado transparente de datos). Si la columna es crítica, puede además ir con Always Encrypted (cifrado de columna donde el motor no ve texto claro). Al consultar vía API (Application Programming Interface, interfaz de programación), la aplicación identifica el rol del sujeto: un administrador autorizado puede obtener el valor completo vía flujo controlado (y uso de CMK (Customer-Managed Key, clave administrada por el cliente) según diseño); un usuario estándar recibe salida enmascarada (p. ej. ****1234) según políticas OAuth2 (autorización delegada; OpenID Connect añade identidad)/OPA (Open Policy Agent, motor de políticas declarativas Rego). En SQL Server, el DDM (Dynamic Data Masking, enmascaramiento dinámico de datos) nativo protege consultas ad hoc de soporte/DBA alineadas con el mismo modelo de etiquetas.

3. Seguridad en tránsito interno (por qué mTLS (TLS (Transport Layer Security, cifrado en tránsito) mutuo, mutual TLS (Transport Layer Security, cifrado en tránsito) entre servicios) o equivalente)

HTTPS en el navegador no cubre el tráfico entre microservicios. mTLS (TLS (Transport Layer Security, cifrado en tránsito) mutuo, mutual TLS (Transport Layer Security, cifrado en tránsito) entre servicios) asegura que el servicio A solo acepta al B si presenta un certificado válido y que el canal es cifrado de extremo a extremo entre cargas. Cumple el espíritu de controles de segregación y seguridad en redes (ISO A.13). Sin mesh, se implementan certificados por servicio o TLS (Transport Layer Security, cifrado en tránsito) mutuo puntual más políticas de identidad — ver capa 7A opcional y anexo.

4. Extracción masiva de datos y Risk engine (SVG)

La protección operativa frente a copia masiva (API (Application Programming Interface, interfaz de programación), GraphQL (lenguaje de consulta tipado sobre API (Application Programming Interface, interfaz de programación), alternativa/complemento a REST (estilo de API (Application Programming Interface, interfaz de programación) sobre HTTP con recursos y verbos)), export CSV, reporting) es en gran parte baseline: límites de tasa, profundidad y coste de queries, paginación estricta, cuotas por usuario/tenant, timeouts y alertas de volumen en SIEM (Security Information and Event Management, correlación de eventos). El Risk engine del pie del diagrama (rosa, tarjeta «App · frontera dura» en #svg-mermaid-opcional) y el bloque «IdP (Identity Provider, proveedor de identidad, p. ej. Entra ID) · PDP (Policy Decision Point, punto de decisión de políticas) · riesgo» son opcionales: correlacionan telemetría y RCO (Request Context Object, contexto de petición) con un PDP (Policy Decision Point, punto de decisión de políticas) para endurecer o denegar en contexto; van después de tener MFA (autenticación multifactor), rate limit y reglas SIEM (Security Information and Event Management, correlación de eventos) mínimas, no en su lugar.

Prioridad inmediata — Cifrado de base de datos

Según la petición recibida: el sistema no dispone actualmente de cifrado en BBDD; este punto es urgente y prioritario respecto al resto de la evolución de arquitectura de seguridad, que se articula como hoja de ruta más amplia.

Objetivo: garantizar confidencialidad de los datos en reposo en el motor de base de datos y en copias (backups, ficheros de datos), alineado con controles típicos ISO 27001 (sistema de gestión de seguridad de la información, SGSI (sistema de gestión de la seguridad de la información, ISO 27001)) / RGPD (Reglamento General de Protección de Datos), sin perder viabilidad operativa.

Fase A — Cifrado en reposo a nivel de servicio (alcance mínimo recomendado como primer entregable)

  • Transparent Data Encryption (TDE (Transparent Data Encryption, cifrado transparente de datos)) en Microsoft SQL Server: cifra archivos de datos y log en disco; transparente para Express/ORM (Object-Relational Mapping, mapeo objeto-relacional) salvo Always Encrypted (cifrado de columna donde el motor no ve texto claro) a nivel columna.
  • Claves bajo control del cliente: en Azure, integración EKM (Extensible Key Management, gestión de claves con módulo externo/HSM (Hardware Security Module, criptografía en hardware)) con Azure Key Vault (u HSM (Hardware Security Module, criptografía en hardware)) para proteger la DMK/DEK de TDE (Transparent Data Encryption, cifrado transparente de datos); alternativa con certificado de servidor según política. Rotación y auditoría de uso documentadas.
  • Validación en entorno no productivo: impacto en rendimiento (habitualmente bajo); ventanas de mantenimiento si hay operaciones de habilitación TDE (Transparent Data Encryption, cifrado transparente de datos) o rotación inicial.

Criterio de hecho: TDE (Transparent Data Encryption, cifrado transparente de datos) activo en SQL Server de producción con material de clave custodiado (EKM (Extensible Key Management, gestión de claves con módulo externo/HSM (Hardware Security Module, criptografía en hardware))/Key Vault o procedimiento equivalente); evidencia de configuración y backups cifrados; documento breve de rotación de clave.

Fase B — Datos sensibles a nivel columna (cuando el riesgo o normativa lo exijan)

  • Always Encrypted (cifrado de columna donde el motor no ve texto claro) (determinístico o aleatorio) para columnas identificadas en inventario de datos personales o secretos; claves maestras en Key Vault; posible impacto en consultas y en capa de aplicación/ORM (Object-Relational Mapping, mapeo objeto-relacional).
  • Clasificación de columnas; revisión de informes, ETL y jobs que no puedan descifrar en texto claro en capas no autorizadas.

Criterio de hecho: lista de columnas cifradas aprobada por negocio/DPO; pruebas de regresión en APIs y reporting; ningún secreto largo en repositorio.

Cadena relacionada (para estimación conjunta)

  • Cifrado en tránsito: TLS (Transport Layer Security, cifrado en tránsito) 1.2+ entre aplicación y SQL (Encrypt=True; sin conexiones sin cifrar en prod).
  • Separación de roles: DBA operativo sin acceso a texto claro de columnas AE cuando proceda; uso de secure enclave si se desea consultar datos cifrados con aislamiento.
  • Auditoría de acceso a datos sensibles (auditoría nativa SQL + correlación en SIEM (Security Information and Event Management, correlación de eventos), ver anexo).

1. MFA (autenticación multifactor) — Tipo, flujo y controles

Tipos de factor (orden de preferencia): FIDO2 / passkeys (phishing-resistant); app Authenticator (TOTP OAuth/OATH); notificación Entra con número matching; SMS solo como excepción documentada (riesgo SIM swap).

Flujo de autenticación (usuarios humanos): usuario accede a la SPA → redirect a Entra ID con PKCE (intercambio de prueba de clave para clientes públicos, RFC 7636) → tras contraseña, Conditional Access exige MFA (autenticación multifactor) si la sesión/política lo requiere → emisión de tokens con amr/acr acorde al nivel reforzado → API (Application Programming Interface, interfaz de programación) valida JWT (JSON Web Token, token firmado de acceso) y scopes.

Controles: políticas Conditional Access (ubicación, riesgo de inicio de sesión, dispositivo administrado); exclusión de cuentas salvo break-glass monitorizada; registro de métodos MFA (autenticación multifactor) y revocación administrativa; protección contra token replay (rotación refresh, detección de reutilización).

Separación: client credentials para servicio-servicio no usa “MFA (autenticación multifactor) de usuario”; allí mTLS (TLS (Transport Layer Security, cifrado en tránsito) mutuo, mutual TLS (Transport Layer Security, cifrado en tránsito) entre servicios) o credenciales de workload + scopes limitados (ver sección servicios).

3. Gestión de claves y secretos

  • Jerarquía: KEK en HSM (Hardware Security Module, criptografía en hardware) / Key Vault → uso vía EKM (Extensible Key Management, gestión de claves con módulo externo/HSM (Hardware Security Module, criptografía en hardware)) en SQL Server para TDE (Transparent Data Encryption, cifrado transparente de datos) / Always Encrypted (cifrado de columna donde el motor no ve texto claro); DEK por servicio para discos y TLS (Transport Layer Security, cifrado en tránsito) internos; sin export de claves maestras.
  • Acceso: Managed Identity por workload; RBAC (control de acceso basado en roles) mínimo; sin secretos estáticos en Git; CI/CD (integración y entrega continuas, Continuous Integration / Delivery) con OIDC (OpenID Connect, identidad federada sobre OAuth2 (autorización delegada; OpenID Connect añade identidad)) para secretos efímeros.
  • Operaciones: rotación programada; solape de versiones JWKS (JSON Web Key Set, conjunto de claves públicas para validar JWT) en rotación JWT (JSON Web Token, token firmado de acceso); procedimiento de emergencia y break-glass auditado.
  • Evidencias: logs de Key Vault (Audit), alertas de uso anómalo, inventario de certificados y fechas de expiración.

4. Seguridad entre servicios (mTLS (TLS (Transport Layer Security, cifrado en tránsito) mutuo, mutual TLS (Transport Layer Security, cifrado en tránsito) entre servicios) y alternativas)

Opción A — Service mesh (p. ej. Istio): sidecars con mTLS (TLS (Transport Layer Security, cifrado en tránsito) mutuo, mutual TLS (Transport Layer Security, cifrado en tránsito) entre servicios) bidireccional, identidad X.509 por pod, políticas L4/L7; observabilidad unificada. Esfuerzo: operación del mesh y políticas.

Opción B — mTLS (TLS (Transport Layer Security, cifrado en tránsito) mutuo, mutual TLS (Transport Layer Security, cifrado en tránsito) entre servicios) “punto a punto” sin mesh completo: certificados corta duración emitidos por CA interna + verificación en cliente/servidor; más ligero si hay pocos pares.

Opción C — Red privada + OAuth2 (autorización delegada; OpenID Connect añade identidad) client credentials: no sustituye cifrado en tránsito; combinar TLS (Transport Layer Security, cifrado en tránsito) con validación de token en cada hop para autorización; mTLS (TLS (Transport Layer Security, cifrado en tránsito) mutuo, mutual TLS (Transport Layer Security, cifrado en tránsito) entre servicios) recomendado donde el modelo de amenaza exija autenticación mutua fuerte entre servicios.

Controles comunes: prohibir confiar solo en IP interna; SVID (SPIFFE Verifiable Identity Document, credencial de identidad de servicio) SPIFFE (identidades de carga de trabajo para mTLS) cuando el entorno sea dinámico (Kubernetes).

5. Seguridad en colas y eventos

  • Transporte: TLS (Transport Layer Security, cifrado en tránsito) hacia broker (Event Hubs / Kafka); SASL SCRAM o Entra ID según producto.
  • Autorización: ACL por topic/partition y por identidad de productor/consumidor; principio de mínimo privilegio.
  • Integridad y no repudio: firma o MAC del mensaje (clave por tenant/servicio desde Key Vault); anti-replay con nonce y ventana temporal.
  • Esquema: Schema Registry + evolución compatible; rechazar payloads que no validen.
  • Reposo: cifrado en discos del broker según plataforma; retención acotada; considerar cifrado de payload sensible en capa aplicación si el broker no debe ver texto claro.
  • DLQ (Dead Letter Queue, cola de mensajes descartados o fallidos): sin datos de más que en cola principal; mismas reglas de acceso; inspección acotada a roles de plataforma.

6. Logging, auditoría y trazabilidad

  • Correlación: trace-id / request-id desde borde hasta base de datos y mensajes; propagación W3C Trace Context.
  • Logs de aplicación: estructurados (JSON); niveles; sin PII (Personally Identifiable Information, datos personales identificativos) ni secretos en texto claro — enmascarado o tokenizado.
  • Auditoría de seguridad: intentos de login, cambios en IAM (Identity and Access Management, gestión de identidades y accesos), acceso admin a datos, uso de Key Vault, políticas Conditional Access; envío a SIEM (Sentinel) con reglas MITRE.
  • Auditoría de datos: auditoría nativa SQL para sensibles; ingestión a almacenamiento inmutable o WORM (Write Once Read Many, almacenamiento inmutable) para cadena de custodia.
  • Retención: plazos por tipo de log (operativo vs legal); RBAC (control de acceso basado en roles) en herramientas de consulta; export para regulador o auditor externo.
  • Trazabilidad de cambios: commits firmados, pipelines con SBOM (Software Bill of Materials, inventario de dependencias) y trazas hacia despliegue (vínculo con anexo DevSecOps (desarrollo, seguridad y operaciones unificados) Capa 8B).

Flujo lógico: tráfico → CDN (Content Delivery Network, red de distribución de contenidos)/WAF (Web Application Firewall, cortafuegos web) → terminación TLS (Transport Layer Security, cifrado en tránsito) → gateway → límites de tasa → capas internas.

Paso 1 — Origen del tráfico (clientes y terceros)

  • 1.1 Identificar canal: usuarios (navegador / SPA), apps móviles o integraciones B2B.
  • 1.2 Fijar contrato: REST (estilo de API (Application Programming Interface, interfaz de programación) sobre HTTP con recursos y verbos), GraphQL (lenguaje de consulta tipado sobre API (Application Programming Interface, interfaz de programación), alternativa/complemento a REST (estilo de API (Application Programming Interface, interfaz de programación) sobre HTTP con recursos y verbos)) o WebSockets; versionado y límites documentados.
  • 1.3 Partners: webhooks firmados, OAuth2 (autorización delegada; OpenID Connect añade identidad) client credentials o authorization code según caso.
  • Registrar orígenes IP / dominios permitidos cuando aplique (lista blanca en WAF (Web Application Firewall, cortafuegos web) o APIM (API (Application Programming Interface, interfaz de programación) Management, puerta de enlace y políticas de APIs)).
  • Definir SLA de latencia y tamaño máximo de payload por canal.

Paso 2 — Azure Front Door (CDN (Content Delivery Network, red de distribución de contenidos) y borde)

  • 2.1 Enrutamiento geográfico y optimización de latencia (reglas por región).
  • 2.2 Mitigación DDoS (ataque de denegación de servicio distribuido) en capa de red (Anycast, absorción en PoP).
  • 2.3 Caché estática en PoP y políticas TTL por tipo de recurso.
  • 2.4 Sondeos de salud del origen y conmutación por error (failover).
  • Validar cabeceras de caché y busting en despliegues.
  • Monitorizar ratio de aciertos de caché y errores 5xx en orígenes.

Paso 3 — WAF (inspección aplicación)

  • 3.1 Activar reglas OWASP (Open Web Application Security Project) CRS y afinar excepciones con riesgo mínimo.
  • 3.2 Cubrir OWASP (Open Web Application Security Project) Top 10 (SQLi (inyección SQL), XSS (Cross-Site Scripting, ejecución de script en contexto de otro sitio), LFI, RFI, SSRF, etc.).
  • 3.3 Capa anti-bot / huella de cliente si el tráfico lo exige.
  • 3.4 Geo-bloqueo o restricción por IP según política de negocio.
  • Registro de falsos positivos y proceso de tuning quincenal.
  • Reglas personalizadas para APIs (paths, JSON, verbos HTTP).

Paso 4 — Terminación TLS (Transport Layer Security, cifrado en tránsito)

  • 4.1 Solo TLS (Transport Layer Security, cifrado en tránsito) 1.2+; preferir 1.3; lista negra de suites débiles.
  • 4.2 Claves efímeras (ECDHE) y cifrado simétrico robusto (p. ej. AES (Advanced Encryption Standard, cifrado simétrico)-GCM (Galois/Counter Mode, modo AEAD)).
  • 4.3 HSTS (HTTP Strict Transport Security, forzar HTTPS) con preload donde proceda; OCSP (Online Certificate Status Protocol, estado de revocación de certificado) stapling habilitado.
  • 4.4 mTLS (TLS (Transport Layer Security, cifrado en tránsito) mutuo, mutual TLS (Transport Layer Security, cifrado en tránsito) entre servicios) para partners B2B (certificados cliente + cadena de confianza).
  • Renovación automatizada de certificados y alertas pre-expiración.
  • Alineación con Key Vault / HSM (Hardware Security Module, criptografía en hardware) para claves privadas (ver Capa 6).

Paso 5 — API (Application Programming Interface, interfaz de programación) Gateway (APIM (API (Application Programming Interface, interfaz de programación) Management, puerta de enlace y políticas de APIs) / Kong)

  • 5.1 Validación de API (Application Programming Interface, interfaz de programación) keys y/o OAuth2 (autorización delegada; OpenID Connect añade identidad) scopes en el borde.
  • 5.2 Pre-validación JWT (firma, audiencia, emisor) antes del backend.
  • 5.3 Enrutamiento por versión y transformación de peticiones/respuestas.
  • 5.4 Validación de esquema (OpenAPI/GraphQL (lenguaje de consulta tipado sobre API (Application Programming Interface, interfaz de programación), alternativa/complemento a REST (estilo de API (Application Programming Interface, interfaz de programación) sobre HTTP con recursos y verbos))) cuando aplique.
  • Políticas por producto: throttling diferenciado, cuotas por suscripción.
  • Registro de correlación x-request-id hacia trazas downstream.

Paso 6 — Rate limiting

  • 6.1 Implementación distribuida (p. ej. Redis) con token bucket / ventana deslizante.
  • 6.2 Límites por IP, por usuario (claims) y por ruta sensibles.
  • 6.3 Respuesta 429 con Retry-After; circuit breaker aguas arriba.
  • 6.4 Listas allow/deny y degradación elegante bajo abuso.
  • Dashboard de picos y alertas sobre ratio 429 vs 2xx.
  • Pruebas de carga que validen límites sin degradar usuarios legítimos.

Infra / API (Application Programming Interface, interfaz de programación) Capa 2 — GraphQL (federación)

Flujo: gateway compone el supergráfico → planifica la query → ejecuta en subgrafos → agrega y aplica políticas de coste/depth. En producción es troncal junto a Express; en el SVG la capa 2 usa el mismo lenguaje visual que el resto de infra (no rosa «opcional»). Los resolvers deben aplicar masking de PII (Personally Identifiable Information, datos personales identificativos) por rol en coherencia con la capa 4 y el DDM (Dynamic Data Masking, enmascaramiento dinámico de datos) en SQL Server.

Paso 1 — Gateway (Apollo Router u homólogo)

  • 1.1 Carga del supergráfico compilado y comprobación en arranque.
  • 1.2 Query planning: minimizar round-trips y detectar ciclos.
  • 1.3 Persisted queries / APQ: rechazar queries arbitrarias en producción.
  • 1.4 Límite de profundidad y complejidad (cost analysis) por petición.
  • Caché de respuesta por operación y clave de usuario/tenant cuando sea seguro.
  • Extensión de trazas OTel (OpenTelemetry, telemetría unificada) con nombre de operación GraphQL (lenguaje de consulta tipado sobre API (Application Programming Interface, interfaz de programación), alternativa/complemento a REST (estilo de API (Application Programming Interface, interfaz de programación) sobre HTTP con recursos y verbos)).

Paso 2 — Subgrafo Auth

  • 2.1 Mutaciones/Queries de login, refresh, logout y desafío MFA (autenticación multifactor).
  • 2.2 Tipos de sesión alineados con tokens emitidos por Entra ID (Capa 3).
  • No exponer detalles internos en errores GraphQL (mapear a códigos estables).

Paso 3 — Subgrafo User

  • 3.1 Resolvers con comprobación de pertenencia (solo datos del sub del JWT (JSON Web Token, token firmado de acceso)).
  • 3.2 Campos sensibles tras políticas OPA (Open Policy Agent, motor de políticas declarativas Rego)/RBAC (Capa 3–4).

Paso 4 — Subgrafo Data

  • 4.1 Entidades federadas y claves @key estables.
  • 4.2 Filtros de multi-tenant obligatorios en cada resolver que toque datos.
  • 4.3 Campos sensibles: máscara o null según rol antes de serializar; misma taxonomía que DDM (Dynamic Data Masking, enmascaramiento dinámico de datos) en base de datos (evitar doble verdad).

Seguridad Capa 3 — Identidad, MFA (autenticación multifactor) y políticas

Flujo: IdP (Identity Provider, proveedor de identidad, p. ej. Entra ID) emite tokens → refuerzo MFA (autenticación multifactor) → formato JWT (JSON Web Token, token firmado de acceso) → RBAC (control de acceso basado en roles) → ABAC (control de acceso basado en atributos)/OPA (Open Policy Agent, motor de políticas declarativas Rego) → sesión en Redis.

Paso 1 — Azure Entra ID (IdP (Identity Provider, proveedor de identidad, p. ej. Entra ID))

  • 1.1 Registro de apps, redirect URIs estrictos y secretos rotados.
  • 1.2 Flujos: authorization code + PKCE (SPA/móvil), client credentials (servicios).
  • 1.3 Conditional Access: ubicación, dispositivo conforme, riesgo de inicio de sesión.
  • 1.4 PIM para roles elevados; Identity Protection para cuentas privilegiadas.
  • Revisión trimestral de consentimientos y permisos de API (Application Programming Interface, interfaz de programación) Graph.
  • Break-glass accounts documentados y monitoreados.

Paso 2 — MFA (autenticación multifactor)

  • 2.1 FIDO2 / passkeys como métodos preferentes; TOTP como alternativa.
  • 2.2 SMS solo como último recurso (riesgo de SIM swap).
  • 2.3 Códigos de recuperación y flujo de revocación de dispositivos.

Paso 3 — Tokens JWT (JSON Web Token, token firmado de acceso)

  • 3.1 Algoritmos asimétricos (RS256/ES256); claves en Key Vault/HSM (Hardware Security Module, criptografía en hardware).
  • 3.2 Vida corta del access token; refresh con rotación y detección de reutilización.
  • 3.3 Claims mínimos necesarios; jti para revocación puntual.
  • 3.4 JWKS (JSON Web Key Set, conjunto de claves públicas para validar JWT) publicado; introspección para clientes confidenciales si aplica.

Paso 4 — RBAC (control de acceso basado en roles)

  • 4.1 Roles de aplicación mapeados a grupos de Entra o roles locales.
  • 4.2 Cuentas de servicio con alcance mínimo y rotación de secretos.
  • 4.3 JIT para acciones administrativas sensibles.

Paso 5 — ABAC (control de acceso basado en atributos) / OPA (Open Policy Agent, motor de políticas declarativas Rego)

  • 5.1 Políticas Rego versionadas; denegación por defecto.
  • 5.2 Contexto: atributos de usuario, recurso, tenant y etiquetas de datos.
  • 5.3 Logs de decisión exportables a SIEM (Capa 8A).

Paso 6 — Redis (sesiones y revocación)

  • 6.1 Sesiones con TTL y renovación deslizante según riesgo.
  • 6.2 Conjunto de jti revocados con expiración acorde al refresh.
  • 6.3 TLS (Transport Layer Security, cifrado en tránsito) en tránsito, ACL Redis, cifrado en reposo según plataforma.

App Capa 4 — Servidor y dominio

Flujo: runtime Node → Express (REST (estilo de API (Application Programming Interface, interfaz de programación) sobre HTTP con recursos y verbos)) + GraphQL (lenguaje de consulta tipado sobre API (Application Programming Interface, interfaz de programación), alternativa/complemento a REST (estilo de API (Application Programming Interface, interfaz de programación) sobre HTTP con recursos y verbos)) (Apollo u homólogo) → rate limiting (capa API (Application Programming Interface, interfaz de programación), antes o después del JWT (JSON Web Token, token firmado de acceso) según política) → middleware de auth → validación → lógica → masking de salida (JSON y campos GraphQL (lenguaje de consulta tipado sobre API (Application Programming Interface, interfaz de programación), alternativa/complemento a REST (estilo de API (Application Programming Interface, interfaz de programación) sobre HTTP con recursos y verbos)) por rol) → ORM (Object-Relational Mapping, mapeo objeto-relacional) → SQL Server con DDM (Dynamic Data Masking, enmascaramiento dinámico de datos) donde aplique. El bloque opcional recoge refuerzos (portal API (Application Programming Interface, interfaz de programación), RCO (Request Context Object, contexto de petición), sanitizer avanzado, IA shield), no el masking troncal.

Paso 1 — API (Application Programming Interface, interfaz de programación) Server (Node.js / Express)

  • 1.1 Proceso bajo usuario sin privilegios; límite de recursos.
  • 1.2 Helmet y cabeceras CSP (Content Security Policy, cabecera anti-XSS)/CORS (Cross-Origin Resource Sharing, política de orígenes en navegador) explícitas (no * en prod).
  • 1.3 Cluster (PM2/K8s) con señales de terminación para drenaje de conexiones.

Paso 2 — Rate limiting en la API (no solo en el gateway)

  • 2.1 Middleware global (express-rate-limit u homólogo) + límites más estrictos en rutas sensibles (login, exportación, búsquedas pesadas).
  • 2.2 Store distribuido en Redis (misma instancia/cluster que sesiones/revocación cuando sea posible) para que el límite sea coherente entre réplicas de la API (Application Programming Interface, interfaz de programación).
  • 2.3 Capas de cuota: por IP (anti-flood), por identidad (sub del JWT (JSON Web Token, token firmado de acceso) o sesión) y por API (Application Programming Interface, interfaz de programación) key en integraciones B2B.
  • 2.4 Respuesta 429 Too Many Requests con Retry-After; métricas y logs correlacionados con trace-id hacia SIEM (Security Information and Event Management, correlación de eventos).
  • 2.5 Complementario al rate limit del API (Application Programming Interface, interfaz de programación) Gateway / Front Door (defensa en profundidad): el gateway corta abuso en el perímetro; la API (Application Programming Interface, interfaz de programación) protege lógica y coste por usuario/ruta.

Paso 3 — Middleware de autenticación

  • 3.1 Verificación de firma JWT (JSON Web Token, token firmado de acceso) vía JWKS (JSON Web Key Set, conjunto de claves públicas para validar JWT) cacheado con refresco seguro.
  • 3.2 Validación temporal (iat, nbf, exp) y audiencia.
  • 3.3 Comprobación de jti contra Redis de revocación.
  • 3.4 Inyección de contexto de seguridad (usuario, roles, tenant) en cada petición (handlers / capa de aplicación).
  • Auditoría de intentos fallidos correlacionados con SIEM (Security Information and Event Management, correlación de eventos).

Paso 4 — Validación de entrada

  • 4.1 Esquemas Zod/Joi alineados con OpenAPI (REST (estilo de API (Application Programming Interface, interfaz de programación) sobre HTTP con recursos y verbos)) y con el contrato GraphQL (variables, inputs, enums) en producción.
  • 4.2 Normalización y saneado; rechazo de campos desconocidos.
  • 4.3 Límites de longitud y formatos (email, ISO8601, enums).

Paso 5 — Lógica de negocio

  • 5.1 Casos de uso aislados; sin lógica sensible en controladores finos.
  • 5.2 Sagas/eventos: idempotencia en comandos críticos.
  • 5.3 Segunda llamada a OPA (Open Policy Agent, motor de políticas declarativas Rego) cuando la regla depende del contenido del recurso.

Paso 6 — Capa ORM (Object-Relational Mapping, mapeo objeto-relacional)

  • 6.1 Solo consultas parametrizadas; prohibido concatenar SQL.
  • 6.2 Pool de conexiones con credenciales desde Key Vault (sin variables en imagen).
  • 6.3 RLS (Row-Level Security, seguridad a nivel de filas) / filtro tenant injected desde contexto de request.

Paso 7 — Data masking en la API (y correlación con SQL Server)

  • 7.1 Políticas por rol/tenant para DNI, email, teléfono, IBAN y demás etiquetas de datos acordadas con compliance.
  • 7.2 REST (estilo de API (Application Programming Interface, interfaz de programación) sobre HTTP con recursos y verbos): DTO de salida o middleware que transforme el payload antes de enviarlo al cliente; GraphQL (lenguaje de consulta tipado sobre API (Application Programming Interface, interfaz de programación), alternativa/complemento a REST (estilo de API (Application Programming Interface, interfaz de programación) sobre HTTP con recursos y verbos)): máscara en resolvers o capa de «field middleware» equivalente.
  • 7.3 Alinear reglas con Dynamic Data Masking (DDM (Dynamic Data Masking, enmascaramiento dinámico de datos)) en SQL Server para que usuarios con menos privilegio no vean columnas en claro ni en API (Application Programming Interface, interfaz de programación) ni en consultas ad hoc.
  • 7.4 Always Encrypted (cifrado de columna donde el motor no ve texto claro) / cifrado de campo para lo que DDM (Dynamic Data Masking, enmascaramiento dinámico de datos) y masking de API (Application Programming Interface, interfaz de programación) no cubran (ver capa 5).

Recomendado u opcional — endurecimiento tipo «best practice» (diagrama extendido)

Piezas que refuerzan Zero Trust y observabilidad sin ser siempre obligatorias en un MVP; útiles para roadmap o mantenimiento evolutivo.

  • Perimetro / contrato: portal OpenAPI/Swagger gobernado; API (Application Programming Interface, interfaz de programación) keys con rotación en APIM (API (Application Programming Interface, interfaz de programación) Management, puerta de enlace y políticas de APIs)/Kong; políticas de cuota también en gateway (coherente con Paso 2).
  • Contexto de petición: Request Context Object (RCO (Request Context Object, contexto de petición)) con userId, tenant, riskScore, atributos ABAC (control de acceso basado en atributos) propagados desde el borde cuando el IdP (Identity Provider, proveedor de identidad, p. ej. Entra ID)/gateway los aporte.
  • Capa app: sanitizer explícito (sanitize-html, express-validator); frontera pre/post-auth clara; motor de riesgo ligero en runtime correlacionado con Redis/SIEM (Security Information and Event Management, correlación de eventos).
  • Respuesta: el masking troncal está en el Paso 7; aquí solo refuerzos (p. ej. plantillas de exportación, vistas materializadas para reporting con redacción adicional).
  • Datos: capa de acceso con políticas antes del ORM (Object-Relational Mapping, mapeo objeto-relacional); clasificación/linaje (Purview u homólogo) cuando el alcance lo exija.
  • Observabilidad: OpenTelemetry (estándar de telemetría, métricas/trazas/logs) end-to-end; capa de procesamiento con redacción de PII (Personally Identifiable Information, datos personales identificativos) en logs; UEBA (User and Entity Behavior Analytics, análisis de comportamiento) alimentada desde SIEM (opcional).
  • IA generativa (si aplica): firewall de prompts, validación de salida y políticas semánticas (RGPD (Reglamento General de Protección de Datos)/ENS (Esquema Nacional de Seguridad, España)) — típicamente opcional salvo productos con LLM (Large Language Model, modelo de lenguaje grande) en producción.

Datos / RGPD (Reglamento General de Protección de Datos) Capa 5 — Persistencia y privacidad

Flujo: datos en SQL Server (acceso desde Express con cadena cifrada) → DDM (Dynamic Data Masking, enmascaramiento dinámico de datos) y RLS (Row-Level Security, seguridad a nivel de filas) según rol de conexión → TDE (Transparent Data Encryption, cifrado transparente de datos) y claves → Always Encrypted (cifrado de columna donde el motor no ve texto claro) / cifrado de campo en columnas críticas → controles RGPD (Reglamento General de Protección de Datos) → copias de seguridad. El masking en API (Application Programming Interface, interfaz de programación) (capa 4, Paso 7) debe seguir la misma taxonomía que las reglas DDM (Dynamic Data Masking, enmascaramiento dinámico de datos) para no filtrar PII (Personally Identifiable Information, datos personales identificativos) por la vía GraphQL (lenguaje de consulta tipado sobre API (Application Programming Interface, interfaz de programación), alternativa/complemento a REST (estilo de API (Application Programming Interface, interfaz de programación) sobre HTTP con recursos y verbos))/REST (estilo de API (Application Programming Interface, interfaz de programación) sobre HTTP con recursos y verbos). Si el estado actual carece de cifrado en BBDD, ver prioridad cifrado en base de datos y el modelo de cifrado en el anexo.

Paso 1 — SQL Server (controles del motor)

  • 1.1 Always Encrypted (cifrado de columna donde el motor no ve texto claro) para columnas ultra sensibles (CMK (Customer-Managed Key, clave administrada por el cliente) en Key Vault mediante proveedor en aplicación o EKM (Extensible Key Management, gestión de claves con módulo externo/HSM (Hardware Security Module, criptografía en hardware)) según modo).
  • 1.2 RLS (Row-Level Security, seguridad a nivel de filas) por tenant_id o equivalente en políticas SQL.
  • 1.3 Dynamic Data Masking (DDM (Dynamic Data Masking, enmascaramiento dinámico de datos)): funciones de máscara por columna y rol de base de datos; alineado con el masking de salida en la API (Application Programming Interface, interfaz de programación) para mismos identificadores de PII (Personally Identifiable Information, datos personales identificativos).
  • 1.4 SQL Server Audit + (opcional) Microsoft Defender for SQL si la instancia es elegible; alertas hacia Sentinel / SIEM (Security Information and Event Management, correlación de eventos) en Azure.

Paso 2 — TDE (Transparent Data Encryption, cifrado transparente de datos) y gestión de claves

  • 2.1 TDE (Transparent Data Encryption, cifrado transparente de datos) habilitado en la base de datos; protector con EKM (Extensible Key Management, gestión de claves con módulo externo/HSM (Hardware Security Module, criptografía en hardware)) y Azure Key Vault cuando el servidor esté en Azure VM (máquina virtual), o cadena de certificados acordada.
  • 2.2 Modelo DEK bajo SMK/DMK y KEK según diseño SQL Server; sin export de material maestro desde HSM (Hardware Security Module, criptografía en hardware).

Paso 3 — Cifrado a nivel campo / aplicación

  • 3.1 AES (Advanced Encryption Standard, cifrado simétrico)-GCM (Galois/Counter Mode, modo AEAD) con IV único por escritura; AEAD (cifrado autenticado con datos asociados) para integridad.
  • 3.2 Tokenización de PAN u otros identificadores regulados.
  • 3.3 Derivación de claves por tenant cuando sea requerimiento legal.

Paso 4 — Cumplimiento RGPD (Reglamento General de Protección de Datos)

  • 4.1 Inventario y clasificación de datos personales.
  • 4.2 Retención por categoría; job de purga y anonimización.
  • 4.3 API (Application Programming Interface, interfaz de programación)/proceso de ejercicio de derechos (acceso, rectificación, borrado, portabilidad).
  • 4.4 Registro de tratamiento y DPIA (Data Protection Impact Assessment, evaluación de impacto en protección de datos) para tratamientos de alto riesgo.

Paso 5 — Backups cifrados

  • 5.1 PITR y copias LTR con pruebas de restauración periódicas.
  • 5.2 Copias inmutables para ransomware; claves en Key Vault.
  • 5.3 RTO/RPO verificados en simulacros documentados.

Claves Capa 6 — Key management (hub crítico)

Rol: concentrar secretos, claves simétricas/asimétricas y certificados; todo componente consume vía identidad administrada + políticas.

Paso 1 — Azure Key Vault

  • 1.1 Separación por entorno (dev/test/prod) y por dominio de blast radius.
  • 1.2 RBAC (control de acceso basado en roles) + políticas de acceso; sin secretos en logs ni pipelines.
  • 1.3 Soft delete y protección contra purga; versionado de secretos.

Paso 2 — Managed HSM (Hardware Security Module, criptografía en hardware)

  • 2.1 Ceremonias de clave y quorum m-of-n para operaciones críticas.
  • 2.2 Claves no exportables; solo operaciones criptográficas dentro del HSM (Hardware Security Module, criptografía en hardware).

Paso 3 — Rotación automatizada

  • 3.1 Calendario 90d/365d según tipo de material criptográfico.
  • 3.2 Periodo de solape JWKS (JSON Web Key Set, conjunto de claves públicas para validar JWT) durante rotación de firmas JWT (JSON Web Token, token firmado de acceso).

Paso 4 — Certificados TLS (Transport Layer Security, cifrado en tránsito) / mTLS (TLS (Transport Layer Security, cifrado en tránsito) mutuo, mutual TLS (Transport Layer Security, cifrado en tránsito) entre servicios) / SPIFFE (identidades de carga de trabajo para mTLS)

  • 4.1 Emisión corta duración para servicios; renovación automática.
  • 4.2 SVID (SPIFFE Verifiable Identity Document, credencial de identidad de servicio) SPIFFE (identidades de carga de trabajo para mTLS) enlazado a identidad de carga de trabajo (K8s/VM (máquina virtual)).

Paso 5 — Consumo en aplicación y CI/CD (integración y entrega continuas, Continuous Integration / Delivery)

  • 5.1 Managed Identity / OIDC (OpenID Connect, identidad federada sobre OAuth2 (autorización delegada; OpenID Connect añade identidad)) desde GitHub Actions hacia Key Vault.
  • 5.2 Escaneo de secretos en PR bloqueando merge si hay hallazgos altos.

Opcional Capa 7A — Service mesh y mTLS (TLS (Transport Layer Security, cifrado en tránsito) mutuo, mutual TLS (Transport Layer Security, cifrado en tránsito) entre servicios)

Flujo: sidecar Envoy intercepta → mTLS (TLS (Transport Layer Security, cifrado en tránsito) mutuo, mutual TLS (Transport Layer Security, cifrado en tránsito) entre servicios) con identidad SPIFFE (identidades de carga de trabajo para mTLS) → políticas OPA (Open Policy Agent, motor de políticas declarativas Rego) en dataplane → telemetría unificada. En el diagrama SVG esta capa aparece en rosa como opcional (evolución típica a Kubernetes/mesh); sin mesh, aplicar alternativas del anexo (TLS (Transport Layer Security, cifrado en tránsito) punto a punto, OAuth entre servicios).

Paso 1 — Istio / mesh

  • 1.1 Inyección de sidecar y descubrimiento de servicios.
  • 1.2 VirtualService/DestinationRule: timeouts, reintentos y partición de fallos.

Paso 2 — mTLS (TLS (Transport Layer Security, cifrado en tránsito) mutuo, mutual TLS (Transport Layer Security, cifrado en tránsito) entre servicios)

ISO / Ops Capa 8A — Observabilidad y auditoría

Flujo: instrumentación OTel (OpenTelemetry, telemetría unificada) → agregación → SIEM (Security Information and Event Management, correlación de eventos) y alertas → retención legal en almacenamiento inmutable.

Paso 1 — OpenTelemetry (opcional / estándar de facto)

  • 1.1 No siempre exigible como tal en ISO 27001 (sistema de gestión de seguridad de la información, SGSI (sistema de gestión de la seguridad de la información, ISO 27001)); alternativa aceptable: logs estructurados + correlación en SIEM (Security Information and Event Management, correlación de eventos).
  • 1.2 Si se adopta: trace context W3C, métricas RED/USE y muestreo explícito.

Paso 2 — Logs centralizados (ELK / Monitor)

  • 2.1 Pipelines que enmascaran PII (Personally Identifiable Information, datos personales identificativos) en índices no conformes.
  • 2.2 Retención y RBAC (control de acceso basado en roles) en Kibana; export para auditoría.

Paso 3 — SIEM (Sentinel)

  • 3.1 Reglas KQL (Kusto Query Language, lenguaje de consulta de Sentinel/Azure Data Explorer) con supresión de ruido y priorización MITRE.
  • 3.2 Playbooks SOAR para contención (bloqueo IP, deshabilitar usuario).

Paso 4 — Auditoría inmutable

  • 4.1 Almacenamiento WORM (Write Once Read Many, almacenamiento inmutable) o append-only con hash encadenado.
  • 4.2 Campos mínimos: quién, qué, cuándo, desde dónde, resultado.

DevSecOps (desarrollo, seguridad y operaciones unificados) Capa 8B — Pipeline CI/CD (integración y entrega continuas, Continuous Integration / Delivery)

Flujo: lint y secret scanning → pruebas (unitarias · integración · E2E) → smoke/regresión en entorno real → SAST (análisis estático de seguridad del código)/Sonar → SCA (Snyk, Trivy) → DAST (análisis dinámico de seguridad sobre aplicación en ejecución) opcional → SBOM (Software Bill of Materials, inventario de dependencias) y firma de artefactos → despliegue con OIDC (OpenID Connect, identidad federada sobre OAuth2 (autorización delegada; OpenID Connect añade identidad)).

Paso 1 — Lint, formato y comprobación estática rápida

  • 1.1 ESLint / Stylelint según stack; Prettier o reglas equivalentes para formato consistente.
  • 1.2 nx affected (o equivalente) para acotar trabajo en monorepo.
  • 1.3 Typecheck (tsc --noEmit, analizadores C# / JVM según caso) en cada PR.
  • 1.4 Secret scanning (GitHub Advanced Security, gitleaks u otra) y bloqueo de merges si hay fugas.

Paso 2 — Tests unitarios

  • 2.1 Jest, Vitest, xUnit o framework alineado al repo; ejecución en CI en paralelo.
  • 2.2 Cobertura con umbral mínimo por paquete o por cambio (no solo global).
  • 2.3 Tests deterministas; aislar red y tiempo cuando sea necesario.

Paso 3 — Tests de integración

  • 3.1 APIs con MSW, supertest o cliente real contra servicio embebido o contenedor.
  • 3.2 Bases y colas con Testcontainers, emuladores o entornos efímeros.
  • 3.3 Contract testing (p. ej. Pact) entre productor y consumidor cuando hay acoplamiento de API (Application Programming Interface, interfaz de programación).

Paso 4 — E2E

  • 4.1 Playwright o Cypress contra staging; datos ficticios, sin PII (Personally Identifiable Information, datos personales identificativos) real.
  • 4.2 Paralelización y reintentos sólo donde no oculten fallos reales.
  • 4.3 Artefactos (trazas, vídeo) en fallo para diagnóstico rápido.

Paso 5 — Smoke y regresión post-deploy

  • 5.1 Smoke tras cada despliegue: health, readiness, rutas críticas de negocio.
  • 5.2 Synthetic monitoring o pruebas canary / blue-green como compuerta antes del tráfico completo.
  • 5.3 Rollback automático si fallan chequeos o métricas (SLO) acordadas.

Paso 6 — SAST (análisis estático de seguridad del código) y calidad de código (Sonar / CodeQL / Semgrep)

  • 6.1 SonarQube o SonarCloud: quality gate, “new code” y hotspots de seguridad.
  • 6.2 CodeQL con SARIF en PR para taint y queries personalizadas.
  • 6.3 Semgrep u otras reglas declarativas para políticas propias del dominio.
  • 6.4 Bloqueo de merge ante severidades acordadas; excepciones auditadas.

Paso 7 — SCA (Snyk, OWASP (Open Web Application Security Project) Dependency-Check, escaneo de imágenes)

  • 7.1 Snyk u OWASP (Open Web Application Security Project) Dependency-Check en dependencias directas y transitivas.
  • 7.2 Política de licencias y PRs automáticos de patch cuando el riesgo lo permita.
  • 7.3 Trivy o similar en imágenes base y bins del pipeline.

Paso 8 — DAST (análisis dinámico de seguridad sobre aplicación en ejecución), SBOM (Software Bill of Materials, inventario de dependencias) y despliegue verificado

  • 8.1 OWASP (Open Web Application Security Project) ZAP (u otro DAST (análisis dinámico de seguridad sobre aplicación en ejecución)) contra entorno de staging; IAST opcional donde aporte valor.
  • 8.2 SBOM (CycloneDX / SPDX) por build y comparación frente a baseline.
  • 8.3 Firmar artefactos (cosign, Sigstore), attest SLSA donde se exija trazabilidad.
  • 8.4 Despliegue con OIDC (OpenID Connect, identidad federada sobre OAuth2 (autorización delegada; OpenID Connect añade identidad)) hacia la nube, sin secretos estáticos en el repo; Key Vault para runtime.
