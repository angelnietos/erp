Arquitectura de seguridad — visión pragmática

Plataforma de gestión de CAE (Certificados de Ahorro Energético) para red de concesionarios (más de 20 marcas, más de 1.000 usuarios), con integración a DGT y entorno administrativo (MITECO / IDAE según proceda). Complemento crítico al documento técnico exhaustivo: prioriza lo ejecutable y recorta ruido.

Veredicto equilibrado. El documento maestro está muy bien estructurado y es propio de un proyecto serio con exigencia ISO / RGPD; parte del detalle se acerca a manual de auditoría más que a hoja de ruta de implementación. Con el volumen y el dominio descritos, la postura enterprise B2B es adecuada; la «fortaleza bancaria» (mesh completo, UEBA avanzado, OTel full, IA shield, etc.) suele ser sobreingeniería salvo que un requisito explícito (cliente, DGT, certificación) lo imponga.

1. Contexto y nivel de riesgo

  • Datos personales (DNI, contacto, firmas de cesión): RGPD en plenitud.
  • Datos de vehículo (bastidor, matrícula, ficha técnica): identificativos y posible inferencia de hábitos; tratar con rigor.
  • Incentivos económicos (hasta ~1.000 €, facturación): riesgo de fraude y manipulación de cesiones / achatarramientos.
  • Administración (DGT y posiblemente MITECO/IDAE): exigen buena autenticación, cifrado, trazabilidad y evidencias en auditoría.
  • Escala: miles de operaciones al año en red de concesionarios — no millones de usuarios finales, pero multi-tenant real (marcas / concesionarios) con obligación de aislamiento y auditoría por operación CAE.

Riesgo global: medio-alto, pero no comparable a banca central o datos clínicos. Objetivo razonable: ISO 27001 «ligero» + RGPD con solvencia + controles alineados con DGT, sin posture innecesaria de sector financiero.

2. Lo que está bien justificado (mantener)

  • Cifrado en base de datos (TDE + claves en Key Vault) como prioridad urgente si hoy no hay cifrado en reposo: higiene mínima, no capricho.
  • Always Encrypted (o equivalente) en columnas muy sensibles (DNI, datos de cesión, bastidor si la política lo exige).
  • Entra ID + Conditional Access + MFA fuerte (FIDO2 / passkeys donde sea posible).
  • Masking coherente API + DDM en SQL Server para datos personales y vistas por rol.
  • Defensa en profundidad razonable: rate limiting (borde + API), validación de entrada, JWT bien gestionado, rotación de secretos, Managed Identities.
  • DevSecOps a esta escala: SAST, SCA, SBOM, firma de artefactos y quality gates — hoy es estándar en equipos medianos-altos.
  • Multi-tenancy fuerte: tenant_id / concesionario / marca en GraphQL, ORM, RLS donde aplique, y en políticas de masking.
  • Auditoría de operaciones CAE: quién genera, modifica o valida cada certificado; correlación con integraciones DGT.

3. Donde huele a sobreingeniería (recortar o diferir)

  • Granularidad del documento: pasos y subpasos al nivel de manual ISO pueden generar parálisis por análisis si no se etiqueta claramente qué es obligatorio en fase 1.
  • Service mesh (Istio) + mTLS «completo» (capa 7A del diagrama largo): complejidad operativa alta; para Node + Azure + SQL Server suele bastar TLS 1.3, Private Endpoint / VNet, Managed Identities y mTLS solo donde la DGT o el integrador lo exijan.
  • Banda rosa / opcionales Mermaid: UEBA avanzado, OTel «full», IA shield, PDP ultra-granular, OpenLineage, etc. — útiles como evolución; un logging estructurado + Sentinel con reglas y retención adecuadas cubre la mayor parte del compliance operativo.
  • Estimaciones agregadas muy altas (p. ej. rangos amplios de cientos de H/H para todo el catálogo): replantear por hitos mínimos viables y fases; el hito de cifrado sigue siendo el más rentable primero.

4. Priorización MoSCoW (versión ejecutable)

Must Hacer ya

  • TDE + Key Vault (y plan de rotación).
  • TLS 1.3 y certificados gestionados; sin secretos en código.
  • Entra ID + Conditional Access + MFA (FIDO2 preferente).
  • Masking API + DDM alineados por rol / tenant.
  • Rate limiting distribuido (al menos borde + API por usuario y, si aplica, por concesionario).
  • Secret scanning + Managed Identities hacia servicios Azure/SQL.
  • Auditoría operativa CAE + Sentinel (o SIEM equivalente) con reglas y retención acordes.
  • Integración DGT según especificación vigente (certificados, mTLS u OAuth según exija el proveedor público).

Should Segunda fase

  • Always Encrypted en columnas críticas acordadas (DNI, datos de cesión, etc.).
  • OPA / políticas como código donde aporte control real (sin expandir al infinito).
  • Logging estructurado, correlación de trace-id, tableros operativos.
  • SBOM + quality gates sólidos en CI/CD.
  • Endurecimiento reforzado de integraciones (colas, webhooks, idempotencia, anti-replay).

Could Solo con presupuesto o requisito explícito

  • Service mesh completo, UEBA avanzado, OpenTelemetry «full stack», IA shield, OpenLineage enterprise, PDP centralizado de máxima granularidad.
  • Reevaluar cuando superéis umbrales claros (por ejemplo >5.000 usuarios, varias integraciones críticas en paralelo, o mandato normativo explícito).

6. Hitos pragmáticos sugeridos

  1. Quick win (3–4 semanas): TDE + Key Vault, TLS end-to-end, MFA reforzado, secret scanning y baseline Sentinel.
  2. Identidad y multi-tenant ( siguiente ciclo): RBAC por marca/concesionario, revisión de aislamiento en API y BBDD, rate limits por identidad/tenant.
  3. Trazabilidad CAE: modelo de auditoría inmutable para «quién hizo qué» sobre cada certificado e interacción con DGT.
  4. Endurecimiento integraciones + DevSecOps: contratos DGT estables, pruebas de regresión de seguridad, SBOM en pipeline.
  5. Fase posterior: opcionales rosa del diagrama largo solo bajo criterio de negocio o auditoría.

7. Estimaciones reales (H/H) — alcance pragmático CAE / DGT

Cifras en horas/hombre (H/H), pensadas para un equipo mixto (cloud/seguridad + backend Node/SQL + algo de QA), sin incluir el paquete «rosa» (mesh Istio, OTel full, UEBA avanzado, banda Mermaid opcional, etc.). Sirven para presupuesto y planning; el desglose granular por tarea sigue en arquitectura_seguridad_ultra_detallada.html § estimación.

Supuestos: 2 FTE dedicados parte del tiempo en el quick win; entornos dev/test/prod ya existentes o alquilables en Azure; SQL Server ya operativo; sin migración de motor de BBDD. La integración DGT lleva rango ancho hasta conocer el perfil oficial (certificados, mTLS, colas, etc.).

Total alcance pragmático (A–G, sin H): aprox. 400 – 720 H/H (suma de extremos por fase: 400 = suma bajos; 720 = suma altos).
Con fase H (Should): 470 – 850 H/H.
En tiempo de calendario (no sumando H/H en serie), con solapes razonables entre B/C/E y parte de F/G: ~5–9 meses con 2–3 FTE equivalentes repartidos en el tiempo.

Contraste con el documento ultra (360–530 H/H en hitos 1–4): allí el Hito 3 incluye Zero Trust en mensajería y matices de mesh; aquí se recorta Istio/service mesh y se sustituye por Private Link + TLS + eventos endurecidos, por eso E es 55–100 H/H frente a 120–180 H/H del ultra. Las fases A–G amplían ligeramente el «perímetro real» (DGT, masking, DevSecOps) que en el ultra no estaban siempre explícitos en una sola suma. Para una propuesta cerrada, conviene fijar A+B+C+D en un único paquete (orden de magnitud 260 – 425 H/H, ~3–5 meses calendario) y negociar E–G–H por separado.
